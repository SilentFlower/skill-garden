# Trellis 可视化图解

以**业务架构师 + 系统架构师 + 可视化设计师**的身份，把架构、流程、业务规则和复杂逻辑转成可复核的图解。不要只画漂亮图；先建立清晰图模型，再生成离线可打开的 HTML/SVG 产物。

## 适用范围

优先使用本 skill：

- **架构图**：系统、服务、组件、部署、依赖关系、数据流。
- **流程图**：角色、触发、主路径、分支、异常、终态。
- **逻辑图**：规则链路、判断条件、因果关系、策略选择。
- **状态图**：状态流转、事件触发、失败 / 回滚路径。
- **兼容旧意图**：用户说“画活动图”、“业务流程图”、“梳理流程”、“draw UML”时，也使用本 skill。

不适用：

- 正式需求提取：使用 `trellis-extract-prd`。
- 三件套校验：使用 `trellis-verify-task`。
- 开发后质量检查：使用 `trellis-check-all`。
- 跨层自动化验证：使用 `trellis-run-full-chain`。

## 核心原则

- **先建模再画图**：先整理图类型、节点、关系、边界、判定、异常、假设，再生成图。
- **不臆测**：不得虚构角色、系统、字段、规则、分支或异常路径；缺信息先问。
- **单文件可复核**：主产物是自包含 HTML + inline SVG，用户可离线打开检查。
- **图文同源**：图下方必须有说明卡片，解释关键节点、关键判定、异常路径和待确认项。
- **兼容旧流程图诉求**：旧 UML / 活动图请求不再输出 `doc/uml/`，统一输出到 `doc/visualize/`。

## 工作流

### 1. 判断图类型

从用户描述中判断主图类型：

| 用户意图 | 图类型 |
| --- | --- |
| 系统、服务、组件、部署、调用链 | 架构图 |
| 业务办理、审批、操作步骤、泳道 | 流程图 |
| 规则、判断、因果、策略 | 逻辑图 |
| 状态、事件、流转、回滚 | 状态图 |

如果一个请求同时包含多种图，先选择最能回答当前问题的一张主图；其他图作为待确认或后续迭代。

### 2. 整理图模型

输出图之前，先在内部整理并在必要时向用户确认：

- **图名**：本图要解释的问题。
- **主体**：角色、系统、组件、服务、外部依赖。
- **关系**：调用、依赖、流转、触发、判断、异常、回滚。
- **边界**：系统边界、组织边界、阶段边界、权限边界。
- **终态**：成功、失败、取消、超时、回滚等结束状态。
- **事实 / 假设 / 待确认**：明确区分用户已给出的事实和为了画图必须确认的信息。

### 3. 澄清规则

当下列信息缺失且会影响图结构时，先问再画：

- 主体是谁：用户、运营、审批人、系统、第三方。
- 入口是什么：触发事件、页面入口、API 调用、定时任务。
- 分支条件是什么：判断字段、阈值、权限、状态。
- 异常怎么处理：失败、拒绝、超时、重复提交、回滚。
- 终态是什么：成功状态、失败状态、是否通知、是否留痕。

一次最多问 3 个关键问题。问题要附推荐答案和取舍；能从仓库、文档、任务文件中查到的事实不要问用户。

### 4. 输出目录和文件

默认输出：

- 主图：`doc/visualize/<slug>.html`
- 截图：`doc/visualize/<slug>.png`（需要在对话中展示时生成）

规则：

- `slug` 使用英文小写 + 连字符，例如 `order-approval-flow`。
- 无法安全命名时，向用户确认 `slug`。
- 同名文件可覆盖；HTML 是当前真源。
- 旧 `doc/uml/` 不再作为默认目录。

### 5. 生成 HTML/SVG

HTML 必须是自包含文件：

- CSS 内联。
- SVG 内联。
- 不使用 JavaScript。
- 不依赖外部渲染服务。
- 可以使用系统字体栈；如使用在线字体，必须说明离线时会降级。

文档结构：

1. Header：图名、图类型、简短副标题。
2. Main SVG：主图区域，深色网格背景，节点和连线清晰。
3. Summary Cards：关键节点、关键判定、异常 / 风险、待确认项。
4. Footer：产物元信息。

## 视觉设计系统

### 语义色板

| 类型 | 填充 | 描边 | 用途 |
| --- | --- | --- | --- |
| 外部参与者 / 外部系统 | `rgba(30, 41, 59, 0.5)` | `#94a3b8` | 用户、第三方、外部平台 |
| 人工动作 | `rgba(8, 51, 68, 0.4)` | `#22d3ee` | 人工提交、审批、运营处理 |
| 系统动作 / 后端服务 | `rgba(6, 78, 59, 0.4)` | `#34d399` | 服务处理、任务执行、API |
| 数据 / 存储 | `rgba(76, 29, 149, 0.4)` | `#a78bfa` | 数据库、缓存、文件、状态记录 |
| 业务阶段 / 平台边界 | `rgba(120, 53, 15, 0.22)` | `#fbbf24` | 阶段、域、平台、组织边界 |
| 判定 / 规则 | `rgba(251, 146, 60, 0.28)` | `#fb923c` | 条件判断、策略选择、分支 |
| 异常 / 拒绝 / 超时 | `rgba(136, 19, 55, 0.4)` | `#fb7185` | 错误、拒绝、超时、回滚 |
| 成功终态 | `rgba(20, 83, 45, 0.42)` | `#4ade80` | 完成、通过、生效 |

### 图形规则

- 节点使用圆角矩形；判定节点可用菱形或带 `?` 标记的规则节点。
- 为避免箭头透过半透明节点，先绘制连线，再绘制节点；复杂节点可使用不透明底层矩形 + 半透明样式层。
- 普通流程用实线箭头；异常、拒绝、超时、回滚用虚线或玫红色线。
- 并行或异步关系必须标注“并行”、“异步”、“事件触发”或具体队列 / 事件名。
- 边界使用虚线大框；图例必须放在不遮挡节点和边界的位置。
- 节点文本要短，细节放到副标题或说明卡片，避免主图拥挤。

### 版式建议

- 架构图：按外部入口 → 接入层 → 服务层 → 数据层 → 外部依赖布局。
- 流程图：按角色泳道或阶段从左到右布局；异常路径从主路径分出后回到失败 / 回滚终态。
- 逻辑图：按输入事实 → 判定条件 → 规则结果 → 输出影响布局。
- 状态图：按状态节点 + 事件箭头布局，失败 / 回滚路径单独突出。

## 渲染 PNG

生成 HTML 后，优先用本地浏览器 / Playwright 截图生成 PNG。示例命令可按环境调整：

```bash
node - <<'JS'
const { chromium } = require('playwright');
const path = require('path');

(async () => {
  const input = path.resolve('doc/visualize/<slug>.html');
  const output = path.resolve('doc/visualize/<slug>.png');
  const browser = await chromium.launch();
  const page = await browser.newPage({ viewport: { width: 1280, height: 900 }, deviceScaleFactor: 2 });
  await page.goto('file://' + input);
  await page.screenshot({ path: output, fullPage: true });
  await browser.close();
  console.log(`saved: ${output}`);
})();
JS
```

如果本地没有 Playwright 或浏览器不可用：

- 保留 `.html` 主产物。
- 明确说明 PNG 生成失败原因。
- 提供可执行兜底：用浏览器打开 HTML 后保存 / 截图，或安装 Playwright 后重试。
- 不要假装 PNG 已生成。

## 输出模板

```markdown
## 可视化图解：<图名>

### 图类型
- <架构图 / 流程图 / 逻辑图 / 状态图>

### 产物
- HTML：`doc/visualize/<slug>.html`
- PNG：`doc/visualize/<slug>.png`（如已生成）

### 图模型
- 主体：<角色 / 系统 / 组件>
- 关系：<调用 / 流转 / 判定 / 异常>
- 边界：<系统边界 / 阶段 / 权限>

### 关键说明
- <关键节点或路径>
- <关键判定>
- <异常 / 回滚>

### 待确认
- [ ] <仍未确认但不阻塞当前图的问题>
```

## 迭代规则

- 用户反馈后，只改被指出的部分，保持其他节点和关系稳定。
- 大幅改图类型、版式或主流程前，先确认修改范围。
- 修改后必须同步更新 HTML；如果已经生成 PNG，也要重新截图。

## 禁止事项

- 不要跳过澄清直接画复杂分支图。
- 不要虚构角色、系统、字段、状态、规则、异常路径。
- 不要只输出文字说明而不生成图。
- 不要只给 Mermaid 代码作为最终产物。
- 不要把旧 UML 诉求继续写入 `doc/uml/`。
- 不要在 PNG 生成失败时假装成功。
