# Fallback Findings

本文件定义 `CHK-*` 主路径问题与 `FBK-*` 兜底问题的根因边界。分类发生在严重度评估之前；分类完成后，两类问题都根据当前实际影响分配 P0/P1/P2，并进入同一个修复、风险接受与通过门禁。

---

## 分类顺序

按以下顺序处理每个独立根因：

1. 符合 `DOC-*` 自动修复白名单：交给文档漂移通道。
2. 根因位于 fail-closed、异常输入、失败路径降级、防御性权限或数据保护、容错或故障可观测性保护：记录为 `FBK-*`。
3. 根因位于主路径逻辑、非兜底需求或契约、验证、真实数据流、兼容性或发布集成：记录为 `CHK-*`。
4. 证据不足以确认问题或保护场景：标记 `部分验证`、`阻塞` 或剩余风险，不得猜测分类。
5. 只有风格偏好、主观重构建议或泛化“更健壮”表述，且没有具体可达场景与验证收益：不报告。

契约是否明确不决定通道。即使 PRD、design、implement、spec 或公开契约已经要求某个兜底行为，只要根因仍是保护路径缺口，就记录为 `FBK-*`；该契约只用于加强证据、影响与严重度判断。

---

## `FBK-*` 根因范围

以下根因优先归入 `FBK-*`：

- fail-closed 保护缺失、失效、被绕过或错误回退为放行；
- 畸形、缺失、重复、冲突、越界或未知输入没有按声明边界处理；
- 外部依赖、读取、解析、迁移或平台能力失败时缺少受控降级；
- 防御性权限、隐私、数据完整性、覆盖或删除保护存在缺口；
- 有具体失败场景和验证方式的额外容错或故障可观测性兜底缺口。

安全、权限或数据问题若根因不在保护路径，仍可归入 `CHK-*`。分类看根因，不看“安全问题通常更严重”之类标签。

---

## `FBK-*` 严格准入

每个 `FBK-*` 必须同时具备：

1. **具体位置**：可定位到文件、契约、命令结果或明确的数据流边界。
2. **可达场景**：说明什么异常、失败或保护条件会触发，不能只写“理论上可能”。
3. **问题证据**：证明当前保护缺失、错误或可被绕过；仅有改进想法不算证据。
4. **保护收益**：说明修复后避免的错误放行、数据损害、权限扩大、失控失败或诊断盲区。
5. **验证方式**：给出可执行测试、命令、故障注入或明确手动步骤。

任一项缺失时，不得为了“先记下来”而生成 `FBK-*`。需要更多环境或业务证据时使用 `部分验证`、`阻塞` 或剩余风险；纯偏好直接不报告。

---

## `CHK-*` 根因范围

以下根因归入 `CHK-*`：

- 主路径功能逻辑错误、非兜底需求或公开契约违背；
- lint、typecheck、测试失败，或缺少当前验收必需的验证；
- 真实数据流断点、字段或类型不匹配、兼容性错误；
- 发布、构建、集成或分发链路阻塞；
- 无法归入具体保护路径的其它已证实问题。

不得把修复困难、影响较低或场景少见当作改列 `FBK-*` 的理由。

---

## 严重度与处置

- `CHK-*` 与 `FBK-*` 分别独立编号，当前修复/重检循环保留原 ID。
- 两类问题都按实际影响分配 P0/P1/P2；严重度不改变通道归属。
- 两类问题都是修复项，都被 `修复全部` 覆盖，也都可以通过混合精确 ID 修复，例如 `修复 CHK-001,FBK-002`。
- 用户可以明确接受当前报告中任一 `CHK-*` 或 `FBK-*` 的风险而不修复；接受风险不改变问题通道、严重度、证据或建议，也不能把问题从报告中删除。
- 风险接受必须能唯一对应当前报告的问题 ID；当前报告只有一个候选时，“这个问题”“不管这个”等明确指代可以解析为该 ID。P0 必须逐项写出精确 ID，不接受“全部”式概括授权。
- 风险接受只适用于当前问题证据和实际 diff；受影响代码、契约、验证结果或问题证据变化后立即失效，必须重新检查和接受。
- `strict pass` 仍要求剩余 `CHK-*` 与 `FBK-*` 均为 0；若所有剩余问题都已被用户有效接受，且无阻塞、无部分验证、无未接受的实质风险，则使用“已接受风险通过”。两种通过都可以进入 interactive、untracked、direct Git、Update-Spec 与 Push 的继续路径。
- 只有未处置的 `CHK-*` 或 `FBK-*` 阻断交互完成链。validated auto-loop 不能代表用户接受风险，仍要求两类问题均为 0 才能 `record ok`。
- `仅保留报告` 只表示停止修复，不构成风险接受，也不能把未处置问题改写成通过。
