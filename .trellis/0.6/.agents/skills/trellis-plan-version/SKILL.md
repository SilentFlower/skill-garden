# 版本开发计划 — 从业务操作到 Wave、工作包与分工

从原始需求全文提取版本范围，先按业务操作与可验收结果划分 Wave，再结合已有能力、团队投入和代码边界拆 Task，形成能用于实际开发、联调和交付的计划。

## 核心原则

1. **业务内容有来源** — 需求与 UI 文案以原始需求为依据；用户已确认的补充决定单独标注。代码现状、人员安排和工程估算不伪装成需求原文。
2. **先覆盖，再规划** — 全文扫描并确认需求覆盖后，按“业务操作 → Wave → 实现缺口 → Task → 分工与排期”推进。
3. **Wave 对应业务操作结果** — 说明谁、在什么前提下、完成哪些操作、得到什么可验收结果；可包含围绕同一结果的多个操作。
4. **Task 是执行工作包** — 上下文连贯、范围明确，有输出、工程验证和消费／集成去向；内部字段、按钮、接口和测试步骤放 Checklist。
5. **协作有责任和交接** — 支持多人按职责协作及单负责人使用 Agent；人员数、技术层和页面数都不是自动拆包依据。
6. **完成分层判断** — Task 按其工程范围及既有生命周期完成；Wave 按真实业务操作验收。Mock、自测、合入或所有 Task 关闭都不能自动证明 Wave 已交付。

## 输入

必需：原始需求文档路径、版本／迭代标识、团队信息。团队信息包括实际职责、技能、可用投入及协作方式，不预设前后端或固定人数。

可选：

- **产物目录**：默认 `doc/<版本>/`，显式指定路径优先。
- **交付偏好**：优先业务场景、提测窗口、截止约束及拆分偏好。
- **开发现状**：已有实现、任务、契约、验证证据及外部前置。
- **规划细度**：近期细化／远期候选，或用户明确要求全版本工作包。

先查现有材料；确实影响边界或日期的未知项向用户澄清，其他未知项标明依据不足，不编造人员、投入、能力或期限。

## 执行步骤

### Step 1: 理解结构、全文扫描与开发约束

#### 1.0 先读后扫

识别需求单元、编号、总表、变更日志和版本标记。不要假设文档有特定格式。

#### 1.1 多策略识别版本变更

| 策略 | 方法 |
|------|------|
| 标记扫描 | 用 `rg` 搜索版本标记，包含段落中间嵌入的标记 |
| 需求总表 | 读取版本、更新内容等列，提取本版本条目 |
| 全文通读 | 逐章识别新增、变更、调整及其完整规则 |

将每个变更定位到需求单元，记录编号／名称、摘要、原文位置与变更类型：整体新增／局部变更／字段级嵌入。旧功能内部的新字段或段落也必须识别，不能只看标题。

#### 1.2 识别散射型变更

搜索同一字段、规则、权限、校验、状态、历史数据和导出在不同入口的关联位置，记录散射组。后续说明主责及消费者，避免遗漏或重复实现。

#### 1.3 读取协作与已有能力

- 从团队信息确认谁能承担哪些工作、实际投入、评审／指导责任；计划支持的 Agent 执行方式也单独记录。
- 有既有开发时核对代码、当前任务、共享契约和证据，区分已完成、部分完成、待核实及尚缺范围。
- 识别仓库／模块、共享文件、公共能力提供方与消费者；未核实的路径或接口标为待核实。
- 记录外部服务、环境、样本和产品决定的就绪条件及负责人，不能默认由未确认的外部团队承担。

### Step 2: 输出需求清单并确认覆盖

```markdown
## <版本> 需求清单

### 扫描统计

- 总表版本条目：X；全文变更：Y；去重需求单元：Z。

### 需求列表

| # | 需求单元 | 功能点 | 变更类型 | 变更摘要 | 原文位置 |
|---|----------|--------|----------|----------|----------|

### 散射型变更

| 散射组 | 功能点 | 涉及需求单元 | 关联位置与处理建议 |
|--------|--------|--------------|--------------------|

### 总表与全文差异

| 仅在总表 | 仅在全文 | 两者都有 | 需核实的差异 |
|----------|----------|----------|--------------|
```

**等待用户确认需求覆盖后，再进入 Wave 与 Task 规划。**

### Step 3: 从业务操作划分 Wave

先列业务角色、目标与操作，再寻找能停下来验收的有用结果。一个独立操作或一组紧密相关操作均可形成 Wave，数量由业务结果与交付目标决定。

每个 Wave 写清：

- ID／名称、业务角色与目标。
- 起始条件：可复用的已有能力、数据、上游交付及外部条件。
- 操作过程与最终结果，覆盖本批次需求、边界和来源。
- 验收场景、通过条件、集成及业务验收责任；未确认人员写待定。
- 提测就绪条件与交付顺序。已有能力可作为前提，无需每批重做整个业务流程。

例如“上传招标文件 → 解析提取 → 查看／调整 → 保存”，结果是清单与原文依据可用、保存后能查回并供后续审核消费；这是粒度示例，不固定项目的 Wave 数量或操作。

对话中的 Wave 表和规划摘要也要保留具体业务对象、关键操作与可观察结果，让读者只看摘要就知道交付什么。例如“输入产品，必要时选择类目后查到报价负责人”，不要只概括为“找到能力”“完成问答”或“链路可用”。压缩篇幅时保留影响操作的差异；摘要措辞调整不自动改变已确认的 Wave／Task 边界，也不把每个操作示例另拆成 Wave。

纯契约、迁移、公共组件和环境准备作为支撑 Task，标明服务哪个业务 Wave。已有 W0 等工程准备标签可保留历史含义，不能当作业务验收完成。

格式扩展、专项算法或历史管理按其改变的业务操作与结果判断归属。业务操作的先后与开发排期分开表达，具备输入条件的工作可以并行。

### Step 4: 识别实现缺口并拆工作包

#### 4.1 拆分与合并依据

优先合并上下文紧密、反复修改同一模型／文件、交接难以稳定或无法分别验证的工作。散射变更由同一主责或有明确契约的小组维护。

允许按实际技术职责拆包，前提是分别有明确输出、工程验证、交接条件和集成去向。后端能力可通过契约及行为验证交付给页面或工作流消费者，无需每个包都独立提供完整用户体验。

多人参与、前后端层次、单页或单接口只是观察信号，不能直接决定建 Task。只有需要独立规划、恢复、验证和合入的工作才建立持久任务；包内操作用 Checklist。

#### 4.2 每包的最小信息

| 信息 | 要回答的问题 |
|------|--------------|
| ID、范围与非范围 | 本包改什么，相关范围归谁，来源需求和散射组是什么？ |
| 责任与代码边界 | 谁主责、谁协作，涉及哪些已核实仓库／模块，共享改动由谁维护？ |
| 输入、输出与交接 | 消费什么契约／数据，交付什么，谁接收，如何判断可以接手？ |
| 工程完成标准 | 本包用什么可观察结果证明完成，依据哪份确认范围或契约？ |
| Wave 归属 | 服务哪个业务操作结果，由谁集成并完成 Wave 验收？ |
| 依赖、风险与未决项 | 缺哪个具体交付，影响什么工作，何时须收敛？ |

可用短说明、表格或材料指针表达，按协作复杂度展开；不要求每个简单工作包额外复制多份文档。一个 Task 可有协作者，分工清单不自动成为子 Task。

#### 4.3 依赖与反碎拆检查

依赖必须写明提供方、消费方、交付内容／契约、接收条件及责任，区分：

- **可开工**：如契约、样例或 Mock 已足够。
- **可联调**：如真实服务、版本和环境已具备。
- **可验收**：如业务数据、样本、产品口径和完整操作路径齐备。

仅阻断实际依赖该条件的工作；共享契约未稳定时明确主责与接力，不能把两个修改方按完全独立并行估算。

检查候选与明确关联的已有父子任务：是否出现无独立输出／验证的字段或步骤包、重复范围、循环等待、无消费者的支撑项、无人收口的业务结果，或过大且上下文不连贯的包。根据实际交接和验证调整，不能凭“规划允许拆分”豁免。

#### 4.4 输出规划及逻辑创建顺序

同一 Wave 的新建候选在计划顺序中聚合；组内按依赖与优先级排列。跨 Wave 支撑项标明首个服务 Wave 及后续消费者。创建顺序用于批量建档，不等同于全部工作必须串行开工。

新建 slug 建议为 `<version>-wNN-tNN-<task-slug>`：`wNN` 是 Wave 顺序，`tNN` 是全版本创建顺序。`--slug` 不含日期前缀，`task.py create` 自动添加日期。人员变化或跨日期补建不要求给已有目录改名。

```markdown
## <版本> 任务拆分与 Waves

### 团队约束与拆分依据

- <实际职责、投入、已有能力和拆／并理由；未知项单独注明>

### Wave 业务操作与验收

| Wave | 业务角色／目标 | 起始条件 | 操作过程 | 可验收结果／来源 | 包含 Task | 集成与验收责任 | 提测就绪条件 |
|------|---------------|----------|----------|-----------------|-----------|----------------|--------------|

### Task 候选与交付

| Task ID／名称 | 范围／非范围 | 来源／散射组 | 主责／协作者 | 代码边界 | 输入与输出／消费方 | 工程完成标准 | 主要／服务 Wave | 风险与未决项 |
|---------------|-------------|-------------|--------------|----------|-------------------|--------------|----------------|--------------|

### 依赖与接力

| 提供方 → 消费方 | 交付内容／契约 | 可开工条件 | 可联调条件 | 可验收条件 | 交接责任／阻断影响 |
|-----------------|---------------|------------|------------|------------|-------------------|

### 需求 -> Task -> Wave 覆盖矩阵

| 需求条目 | 原文位置 | 主责／配合 Task | Wave／业务结果 | 当前覆盖与证据 |
|----------|----------|----------------|---------------|----------------|

### Task 创建顺序

| 创建序号 | Wave／支撑归属 | Task ID | Slug 建议 | 依赖与排序原因 | 当前细化／创建范围 |
|----------|---------------|---------|-----------|----------------|-------------------|

### 争议／待确认

- <范围、分工、操作粒度或交付顺序中仍需决定的项>
```

**等待用户确认 Wave、Task 边界和协作安排后，再继续工时评估。** 本 Skill 生成规划，不自动创建 Task 或外部任务卡。

### Step 5: 工时评估

新计划默认使用**小时（h）区间**，保留 `开发计划-工时评估.md` 入口。按当前人＋Agent 的协作方式及净缺口估算，列结构根据实际职责和工作内容裁剪。

- 说明工时记录的是工作包作业耗时还是人工投入，同一张表口径一致；人工参与、Agent 自主执行、外部等待分别说明，重叠活动不重复加总。
- 将实现、自测、联调、验收修复以及必要的设计、评审、指导和交接计入相应阶段；父级汇总不重复计子项工时。
- 根据同类已验收工作包的可核实记录、实际复用与本包未知项给出区间；仅有任务创建／完成日期不能证明有效工时。无依据时写待估、原因及下一检查点，不为填满表格编造数字。
- 不将历史人工人天机械乘以 8，或套固定 AI 提速倍率当作当前估算。保留历史原单位和依据，实际开发方式改变后重估剩余工作。
- 工时与日历交付时间分开；结合依赖、串并行、人员可用小时和等待推导排期，不把各包小时简单相加或除以人数承诺日期。
- 同一人承担的多个关键路径共享容量；Agent 并行也受共享契约、改动冲突和验证资源限制。
- 优先级以需求文档和已确认补充决定为依据；已完成范围按证据扣除，接手成本、暂停条件和旧日期重新核实。完成后有可用记录再回填实际值与偏差，逐步校准，不能从提交时间推断人工工时。

工时表至少说明工作包、剩余范围、阶段小时区间、合计口径、依据／不确定性；分阶段估算仅在有依据时填写。近期先明确可验证的检查点，远期范围保留依赖和待估条件。目标日期与当前预测分别标注，不能将期望日期写成测算结论。

### Step 6: 校验分工与排期

将候选责任细化成近期可执行安排：谁提供、谁消费、何时交接、谁集成验收。说明可以并行的工作、必须接力的共享修改、关键路径和阻断项的影响。

在 `开发计划-工时评估.md` 输出按实际职责组织的工作包估算和人员安排，至少能看出每人的可用小时、承担工作包、评审／指导／联调投入、交接节点与近期交付；未确认日期标为待定。与候选表共用责任和范围依据，不另造一套个人任务编号。

人员替换时分别记录当前主责与历史交付人，保留稳定 ID、原完成状态和证据；只重新估实际剩余范围。估算发现容量或边界不成立时，回到受影响规划作局部调整，不反复确认未变化的决定。

远期可滚动细化；用户明确要求全版本工作包时覆盖完整确认范围。规划细度与实际建档范围分别写明，不能默认把所有候选物化或擅自省略用户指定范围。

### Step 7: 保存产物与交接

默认保存到 `doc/<版本>/需求清单.md`、`任务拆分与waves.md`、`开发计划-工时评估.md`；显式目录优先。分工、接力和进度视图优先从同一规划派生，不强制增加个人台账。

- `trellis-extract-prd` 继承来源、Wave 业务结果、工作包责任与交接，只创建用户指定范围。
- `trellis-verify-task` 核对原文、规划及已创建的关联任务／子任务，检查覆盖、粒度、责任与集成条件。
- 工程完成和 Wave 业务验收分别保留证据；规划更新、任务迁移或改派不改变业务完成事实。

## 反模式

- 只看总表／标题，漏掉字段级嵌入或散射变更。
- 先按人员或技术层分任务，再反推 Wave；每个按钮自动建 Wave，或每人复制一套 Task。
- 以“每包必须有完整 UI 业务闭环”否定有稳定交接与工程验证的技术分工。
- 只有 Task 号依赖，没有具体交付、就绪条件和接收人；候选合理却放任实际子任务继续碎拆。
- 把纯技术准备、自测、合入、任务关闭或元数据整理当成 Wave 业务验收。
- 忽略共享容量、评审与联调，沿用过期工期或把换负责人当作换需求。
- 为人员展示或目录自然排序强制改名历史任务，或重复维护多份相互冲突的分工事实。
